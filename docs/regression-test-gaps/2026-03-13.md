## 1 — `ConcurrentQueue.h`: zero unit tests for a multi-threaded component (High Risk)

**Commits:** #2249 (rocmlir-tuning-driver improvements)

`ConcurrentQueue` is a new adaptive-capacity MPMC queue that backs the tuning driver's
producer-consumer pipeline. The commit fixed several bugs (double-use of `minCapacity`,
capacity-shrink logic, `done`-flag races) but the component has **no unit tests at all**.

### Risky behaviour now uncovered

- **Adaptive capacity**: `pop()` grows `currentCapacity` by 1 when the queue was empty
  (starved); shrinks by half after `fedShrinkThreshold` consecutive non-empty pops.
  An off-by-one silently deadlocks or drops items.
- **`terminate()` wakeup**: must wake all blocked `push()`/`pop()` callers; if the
  `notify_all` fires before the `done` store, callers sleep forever.
- **`push()` after `terminate()`**: must return `false` without blocking; if the early-exit
  check races with `wait()`, items can be pushed to an already-finished queue.

### Suggested test file

`mlir/unittests/TuningDriver/ConcurrentQueueTest.cpp` (Google Test)

```cpp
// unbounded_queue: push N items single-threaded, pop all, verify order and count
// bounded_queue_blocks_when_full: one producer, one consumer with delay; no items lost
// terminate_wakes_blocked_pop: terminate while pop() is waiting; verify returns false
// terminate_wakes_blocked_push: bounded queue at capacity, terminate; push() returns false
// capacity_adapts: fill/drain repeatedly; verify currentCapacity grows and shrinks
// concurrent_producers_consumers: 4×4, N=10 000 items; verify sum matches expected
```

## 2 — `perfRunner.py` tuning DB key schema change: no Python unit tests (High Risk)

**Commits:** #2248 (Extend tuning db key with num\_cu and num\_chiplets), #2259 (Use arch
when writing to tuningDB)

The DB key changed from `(arch, config)` to `(arch, num_cu, num_chiplets, config)`.
`parse_tuning_db_line` and `read_tuning_db` changed their signatures and logic, and
`tuningRunner.py`'s `OutputFileWriter` was changed to write `arch` instead of `chip`.
**No Python tests exist for any of these functions.**

### Risky behaviour now uncovered

- A mismatch between writer (tuningRunner) and reader (perfRunner) silently causes every
  DB lookup to miss → degraded to random / N/A performance, undetectable without a
  numerical comparison.
- Three format branches (legacy 3-column, v2 4-column, v3 5-column) all changed; a
  regression in legacy/v2 parsing silently ignores tuning DB entries in the field.
- New `fallback_num_cu / fallback_num_chiplets` parameters default to `0`; if a caller
  omits them the lookup key never matches a DB written with real values.
- `ValueError` on malformed entries now prints-and-skips; the print path is untested.

### Suggested test file

`mlir/utils/performance/tests/test_perfRunner.py` (pytest)

```python
def test_parse_tuning_db_line_legacy():
    result = parse_tuning_db_line(["gfx90a", "cfg", "v2:1,2"], 64, 1)
    assert result == ("gfx90a", 64, 1, "cfg", "v2:1,2")

def test_parse_tuning_db_line_v2():
    result = parse_tuning_db_line(["gfx90a", "128", "cfg", "v3:..."], 0, 2)
    assert result == ("gfx90a", 128, 2, "cfg", "v3:...")

def test_parse_tuning_db_line_v3():
    result = parse_tuning_db_line(["gfx90a", "128", "4", "cfg", "v3:..."])
    assert result == ("gfx90a", 128, 4, "cfg", "v3:...")

def test_parse_tuning_db_line_malformed_returns_none():
    assert parse_tuning_db_line(["only_two"]) is None

def test_read_tuning_db_roundtrip(tmp_path):
    db_file = tmp_path / "tuning.tsv"
    db_file.write_text("gfx942\t110\t2\tconfig\tv3:1,2,3\n")
    db = read_tuning_db(str(db_file), fallback_num_cu=110, fallback_num_chiplets=2)
    assert db["gfx942", 110, 2, "config"] == "v3:1,2,3"

def test_read_tuning_db_malformed_line_skipped(tmp_path):
    db_file = tmp_path / "tuning.tsv"
    db_file.write_text("bad_line\n")
    db = read_tuning_db(str(db_file))
    assert db == {}
```

## 3 — `BooleanElementwiseConverter` (`migraphx.greater` / `migraphx.equal`): missing dtype coverage (Medium Risk)

**Commit:** #2234

The new converter always uses `arith.cmpi sgt` for `Greater` on integer types,
regardless of signedness. Tests only cover `i32`, `si32`, and `f32`.

### Risky behaviour now uncovered

- `Greater` on unsigned integer inputs (`ui32`) uses `sgt` (signed) instead of `ugt`
  (unsigned) → wrong results for values above `INT32_MAX`.
- `f16`/`bf16` paths use `arith.cmpf ogt` + `arith.uitofp` — correct path, but
  not yet tested; a regression here would silently corrupt bool-masked models.
- Broadcasting inputs: converter assumes identity affine maps (same shapes); mis-shaped
  inputs would produce incorrect indexing with no error.

### File to update

`mlir/test/Conversion/MIGraphXToLinalg/migraphx-to-linalg-boolean.mlir`

Add:
- `@func_greater_f16` — verify `arith.cmpf ogt` + `arith.uitofp` to `f16`
- `@func_equal_f16` — same for `equal`
- `@func_greater_chained` — result fed into another op (catches wrong result type)
- Evaluate whether `migraphx.greater` on unsigned int types should use `ugt`

## 4 — Attention softmax: `MaxNumFOp` vs `MaximumFOp` — no NaN-specific unit test (Medium Risk)

**Commit:** #2258

`GridwiseGemmToBlockwise.cpp` now uses `arith.maxnumf` (NaN-ignoring) instead of
`arith.maximumf` (NaN-propagating). A future refactor reverting this would silently
corrupt softmax outputs whenever NaN scores appear (e.g., from `-inf` masking).

The `arcp` fast-math flag on the new `arith.divf` is also untested: if the denominator
is exactly zero, `arcp` produces `inf * 0 = nan` instead of `0.0`.

### Suggested test file

`mlir/test/Dialect/Rock/lowering_blockwise_broadcast_reduce.mlir` (or new file)

Add a LIT test that lowers an attention op and checks:
1. `arith.maxnumf` appears in output (not `arith.maximumf`)
2. `arcp` flag is present on the final `arith.divf`

## 5 — `firstCausalMaskIter` optimization: off-by-one risk (Medium Risk)

**Commit:** #2258

The new optimization skips element-wise masking for early M-loop iterations:

```
firstCausalMaskIter = (minQEffective + 1) / MPerBlock
```

With GQA `minQEffective` is divided by `numRepeatsGQA` first, adding another rounding.
Current tests only exercise shapes where `firstCausalMaskIter = 0` (all blocks masked).

### File to update

`mlir/test/Dialect/Rock/gridwise_attention_accel_lowering.mlir`

Add a test with `seqLenQ=64`, `seqLenK=128`, `MPerBlock=32`, `NPerBlock=32`:
- `firstCausalMaskIter` should be **1** (first block unmasked, second needs masking)
- `FileCheck` should verify `arith.cmpi uge, %mLoopIV, %c1` in the generated code
  (conditional masking, not unconditional on every iteration)

## 6 — Sliding window attention: no edge-case tests (Medium Risk)

**Commit:** #2240

Sliding window masking is tested with one shape (`seqLen=384`, `windowSize=64`,
`splitKV=8`). The following edge cases are untested:

| Edge case | Why it matters |
|-----------|---------------|
| `windowSize = 0` | Should mask all K positions; might produce unmasked attention |
| `windowSize >= seqLen` | Should be equivalent to no masking; could apply partial masking |
| `windowSize` not a multiple of the K tile size | Block-boundary alignment differs from aligned case |
| Sliding window **without** `currentSeqLen` | Should error or no-op, not silent wrong compute |
